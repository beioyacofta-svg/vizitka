# AI-ассистент запуска творческих проектов — Спецификация

## Executive Summary
Telegram-бот на базе LLM, который через короткий диалог превращает сырую идею творческого предпринимателя (мастера, дизайнера, преподавателя, самозанятого) в реалистичный план запуска: цель, ценность для клиента, бюджет, риски, материалы и — главное — конкретное первое действие. В отличие от обычных планировщиков, бот не хранит задачи, а помогает решить, что делать, в каком порядке и от чего отказаться.

## Problem Statement
Целевой пользователь понимает, что хочет начать творческое дело, но не может самостоятельно собрать это в понятный план и правильную последовательность действий. Без продукта это выливается в бесконечную подготовку: человек утопает в деталях, тратит время и деньги на лишнее, откладывает старт или тратится на неважное до появления первого клиента.

## Success Criteria
Пользователь доходит до первого действия из плана и **возвращается в бот снова** — либо чтобы свериться с планом, либо чтобы начать новый проект. Возврат — основная метрика ценности продукта на MVP-этапе.

## User Personas
- Мастера, дизайнеры, преподаватели, самозанятые — люди с творческим/ремесленным навыком, но без предпринимательского опыта.
- Смешанная техническая/деловая подкованность: часть пользователей знает базовые бизнес-термины (ЦА, воронка), часть — нет. Язык бота должен быть простым бытовым, без жаргона, но не примитивным для тех, кто разбирается.

## User Journey
1. Пользователь пишет `/start`.
2. Бот ведёт **гибридный диалог**: есть заданная структура вопросов (проблема/цель, аудитория, время, бюджет, навыки), но ответы даются в свободной форме, а бот адаптирует следующий вопрос под предыдущий ответ.
3. Если ответ расплывчатый/неопределённый (например, «не знаю, сколько времени есть») — бот **уточняет вопросом**, а не подставляет догадку молча.
4. В конце диалога пользователь получает:
   - план на 7 или 30 дней (по этапам);
   - явно выделенное **первое действие**, которое можно сделать сразу;
   - примерный бюджет;
   - риски;
   - список необходимых материалов.
5. Пользователь может вернуться в бот позже — проект и план сохранены, можно свериться с прогрессом или начать новый проект.

## Functional Requirements

### Must Have (P0)
- Гибридный диалоговый интерфейс в Telegram (структура + свободный текст).
- Уточняющие вопросы при расплывчатых/неполных ответах (бюджет, время и т.п.).
- Генерация плана на 7 или 30 дней с этапами.
- Явное выделение единственного первого действия.
- Расчёт примерного бюджета, списка рисков и материалов.
- Постоянное хранение проектов/диалогов пользователя между сессиями (возврат и продолжение/сверка с планом).
- Подписка с оплатой через российский платёжный сервис, с trial-периодом.

### Should Have (P1)
- Возможность вести несколько проектов на одного пользователя.
- Напоминание/возврат к первому действию, если пользователь долго не отвечает.

### Nice to Have (P2)
- Рост в полноценную платформу: контроль прогресса по этапам, AI-помощь по контенту, клиентским коммуникациям и запуску бизнеса (за пределами MVP).

## Technical Architecture

### Data Model
- **User**: telegram_id, статус подписки, дата начала trial.
- **Project**: id, владелец, исходное описание идеи, статус диалога, дата создания.
- **Plan**: привязан к проекту, горизонт (7/30 дней), этапы, первое действие, бюджет (оценочный, не точные личные доходы), риски, материалы.
- Данные о личных доходах/накоплениях пользователя **не собираются** — только оценочный бюджет на проект.

### System Components
- **Диалоговый слой** — реализуется через no-code/AI-инструмент (например, сценарии диалога и промпт-логика для Telegram), отвечает за сбор ответов и вызов LLM.
- **Сервисный слой (код)** — отдельный компонент вне no-code-платформы, отвечает за:
  - интеграцию с российским платёжным сервисом и логику подписки/trial;
  - постоянное хранение проектов и планов (база данных);
  - выдачу истории проектов пользователю при возврате.
- **LLM-слой** — Claude Haiku 4.5 для ведения диалога, уточняющих вопросов и генерации плана. Приоритет отдан качеству диалога и многошаговому рассуждению над стоимостью токенов (сравнивался с GPT-5 mini — тот дешевле и даёт гарантированный JSON, но слабее в связном диалоге на русском).

### Integrations
- Telegram Bot API.
- Российский платёжный сервис (конкретный провайдер — ЮKassa/Сбер и т.п. — уточняется отдельно) для подписки.
- Claude API (Haiku 4.5) для генерации диалога и плана.

### Security Model
- Стандартная защита персональных данных (описания проектов, планы, оценочные бюджеты не считаются высокочувствительными).
- Платёжные данные обрабатываются на стороне платёжного провайдера, не хранятся в системе напрямую.
- Точные личные доходы/накопления пользователя не запрашиваются и не хранятся — только оценочный бюджет на проект.

## Non-Functional Requirements
- **Производительность**: не определена явно — MVP без прогноза нагрузки; закладывать простую, легко обслуживаемую архитектуру, а не rассчитывать на масштаб с первого дня.
- **Масштабируемость**: открытый риск — точный ожидаемый объём пользователей в первые 1–3 месяца не определён. Рекомендуется закладывать архитектуру, которую один человек может обслуживать без DevOps-нагрузки.
- **Надёжность**: поддержку после запуска ведёт единственный человек (фаундер) — важно минимизировать ручные операции, инфраструктурную сложность и точки отказа.
- **Безопасность**: см. Security Model.

## Out of Scope (для MVP)
- Полноценная платформа с проектным менеджментом, контролем прогресса по этапам, AI-помощью по контенту и клиентским коммуникациям — переносится на будущие версии.
- Точный учёт личных финансов/доходов пользователя.
- Telegram Payments/Stars как способ оплаты (выбран внешний российский платёжный сервис).

## Open Questions for Implementation
- Конкретный российский платёжный провайдер (ЮKassa, Сбер и т.д.) и способ его интеграции с no-code-слоем диалога.
- Конкретный no-code/AI-инструмент для диалоговой логики, совместимый с внешним кодовым сервисом оплаты/базы данных.
- Ожидаемый масштаб пользователей в первые 1–3 месяца — не определён, требует отдельного решения перед выбором хостинга/БД.
- Длительность и условия trial-периода подписки.
- Логика поведения бота при повторном заходе: сверка с существующим планом vs. создание нового проекта — нужно продумать конкретный UX-переход.

## Appendix: Research Findings

### Выбор LLM (Claude Haiku 4.5 vs GPT-5 mini)
- **Цена**: Claude Haiku 4.5 — $1/$5 за 1M токенов (вход/выход); GPT-5 mini — $0.25/$2 за 1M токенов. GPT-5 mini заметно дешевле в эксплуатации.
- **Структурированный вывод**: GPT-5 mini даёт гарантированный JSON по схеме; Claude Haiku 4.5 иногда оборачивает JSON текстом/markdown-разметкой, требуя пост-обработки.
- **Контекст**: у GPT-5 mini окно ~400K токенов против ~200K у Claude Haiku 4.5.
- **Качество диалога**: Claude Haiku 4.5 сильнее в многошаговом рассуждении и связном диалоге — что критично для творческого сценария на русском языке с уточняющими вопросами.
- **Решение**: выбран Claude Haiku 4.5 — качество диалога важнее экономии на токенах для MVP.

### Противоречие no-code vs. требования продукта
No-code инструменты (Manychat и подобные) плохо интегрируются с российскими платёжными системами и сложной логикой подписки/постоянного хранения. Решение — гибридная архитектура: no-code для диалоговой логики, отдельный код/сервис для оплаты и базы данных.
